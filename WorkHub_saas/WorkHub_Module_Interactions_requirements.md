## 1. Module Integration Overview

### 1.1 Purpose

WorkHub SCLAN M-08 is the field execution layer of the SCLAN platform. It receives tasks generated by upstream modules (PC-13, PFE, M-02, PPT), manages worker time and materials during execution, records completion with dual-confirmation, and feeds structured completion data back to billing and audit systems.

### 1.2 Platform Modules in Scope

| Module | Full Name | Primary Responsibility |
|--------|-----------|----------------------|
| WorkHub M-08 | WorkHub SCLAN Field Execution | Task receipt, worker dispatch, time/materials tracking, completion records |
| PFE | Programming and Field Environment | Live bus configuration editor, module context assignment, filter matrices, scene editor |
| PC-13 | Quota Anomaly Detection | Current/voltage monitoring, fault event generation, fault lifecycle management |
| M-02 | Energy Intelligence | Energy quota management, Deep Sleep scheduling, consumption analytics, quota re-baselining |
| PPT | Project Planning Tool | Project and milestone planning, task generation, capacity overview, milestone completion |

### 1.3 Architectural Principles

- **REQ-ARCH-01:** All inter-module communication shall occur via a shared event bus using WebSocket transport with an async message queue for reliability.
- **REQ-ARCH-02:** WorkHub tasks shall carry module-specific reference fields (`pfe_ref_type`, `pfe_ref_id`, and module origin identifier) to preserve traceability back to the originating system.
- **REQ-ARCH-03:** Completion records generated by WorkHub shall be structured and machine-readable to enable automatic invoice line generation in the billing subsystem.
- **REQ-ARCH-04:** The audit log shall be a shared resource accessible to all integrated modules; all significant state transitions shall write to it with a timestamp, actor, and originating module.
- **REQ-ARCH-05:** No module shall block on a synchronous response from WorkHub; all triggers shall be fire-and-confirm via the event bus.

### 2.1 PC-13 Fault → Field Resolution → Auto Invoice Line

**Reference Site:** Hotel Mitte — flickering lights, bus segment Zone-B, Node DN-07

#### 2.1.1 Trigger Requirements

- **REQ-S1-01:** PC-13 shall raise a fault event on the event bus when a quota anomaly is detected on a monitored bus segment. The event payload shall include: segment identifier, node identifier (DN-07), anomaly type, timestamp, and severity level.
- **REQ-S1-02:** Upon receiving a PC-13 fault event, WorkHub shall automatically create a task with the following fields populated:
  - `pfe_ref_type`: `fault`
  - `pfe_ref_id`: fault reference ID (e.g., `fault_9f3a`)
  - Task type: field resolution
  - Source module: PC-13
  - Target site and segment inherited from fault event

#### 2.1.2 Worker Notification Requirements

- **REQ-S1-03:** WorkHub shall deliver an inbox notification to the assigned worker within 30 seconds of task creation.
- **REQ-S1-04:** The task detail view shall surface the PC-13 fault reference ID and segment location so the worker can navigate directly to the affected node.

#### 2.1.3 Field Execution Requirements

- **REQ-S1-05:** The worker shall be able to log resolution steps within the task, including: inspection findings, parts replaced (connector, cable), and any tool or instrument used.
- **REQ-S1-06:** WorkHub shall record material consumption (replacement cable, connector) against the task for downstream billing.
- **REQ-S1-07:** The worker shall be able to initiate a BOPT (Bus Optimisation) re-run from within the task context once physical repair is complete.

#### 2.1.4 Completion and Billing Requirements

- **REQ-S1-08:** Upon task completion (dual-confirmation satisfied), WorkHub shall emit a completion event containing: labour hours, materials consumed, task reference, and fault reference ID.
- **REQ-S1-09:** The billing subsystem shall automatically generate an invoice line for labour and materials from the WorkHub completion event payload.
- **REQ-S1-10:** The invoice line shall carry the fault reference ID (`fault_9f3a`) as a line-item reference for client-facing documentation.

#### 2.1.5 Fault Closure and BOPT Requirements

- **REQ-S1-11:** WorkHub completion shall trigger a close-fault event back to PC-13 via the event bus, carrying the fault reference ID.
- **REQ-S1-12:** PC-13 shall mark the fault as closed upon receipt of the WorkHub close-fault event.
- **REQ-S1-13:** PC-13 shall re-trigger BOPT optimisation for the affected bus segment at restored bus speed after fault closure.

### 2.2 New Installation Commissioning (8-Step PFE State Machine)

**Reference Site:** Villa Rosenberg — Domain Node installation

#### 2.2.1 PPT Task Generation Requirements

- **REQ-S2-01:** PPT shall create a project record and a corresponding task set for new installation commissioning.
- **REQ-S2-02:** PPT shall emit a task-assignment event on the event bus, targeting WorkHub, for each task in the commissioning task set.
- **REQ-S2-03:** The task-assignment event shall include: project ID, milestone ID, task type (Domain Node installation), site identifier, and assigned worker.

#### 2.2.2 PFE State Machine Requirements

- **REQ-S2-04:** WorkHub shall expose an 8-step PFE commissioning state machine for Domain Node installation tasks. Steps shall be executed in the following fixed sequence:

  | Step | Name | Description |
  |------|------|-------------|
  | 1 | Mount | Physical mounting of the Domain Node |
  | 2 | Network | Network connectivity establishment |
  | 3 | PFE Setup | Initial PFE configuration for the node |
  | 4 | Verify | Verification of PFE configuration |
  | 5 | Done | Commissioning sign-off |

  Steps 6 through 8 shall be defined per project configuration and documented in the associated task set from PPT.

- **REQ-S2-05:** The state machine shall prevent advancement to a subsequent step unless the current step is recorded as complete by the worker.
- **REQ-S2-06:** Each step completion shall be recorded with: worker ID, timestamp, step identifier, and any notes or measurements entered.

#### 2.2.3 PFE Live View Synchronisation Requirements

- **REQ-S2-07:** WorkHub shall emit a step-completed event to PFE after each state machine step is recorded as done.
- **REQ-S2-08:** PFE shall update its live view to reflect the current commissioning step in real time upon receipt of each step-completed event.

#### 2.2.4 WorkHub Timer Requirements

- **REQ-S2-09:** WorkHub shall provide a per-step timer that the worker can start and stop. Timer data shall be stored per step and aggregated for the full task.
- **REQ-S2-10:** Done reports shall be required at each step completion; the system shall not allow step advancement without a submitted report.

#### 2.2.5 Final Sign-off Requirements

- **REQ-S2-11:** The final commissioning sign-off (Step 5 / Done) shall require dual-confirmation: worker submission plus customer eIDAS-compliant digital signature.
- **REQ-S2-12:** Upon dual-confirmation, WorkHub shall generate and deliver a client copy of the completion record, incorporating the eIDAS signature.
- **REQ-S2-13:** WorkHub shall emit a milestone-complete event to PPT, referencing the project ID and milestone ID.
- **REQ-S2-14:** PPT shall mark the associated milestone as complete upon receipt of the milestone-complete event from WorkHub.

### 2.3 PnP Module Discovery → Configuration Task → Billable Add-on

**Reference Site:** Office Park AG — floor 3, new dimmer module

#### 2.3.1 PFE PnP Detection Requirements

- **REQ-S3-01:** PFE shall detect newly connected modules via the PnP (Plug-and-Play) mechanism on the bus and emit a module-discovered event on the event bus.
- **REQ-S3-02:** The module-discovered event shall include: module type, module address (e.g., `0x0042`), bus segment, site, and discovery timestamp.

#### 2.3.2 WorkHub Task Creation Requirements

- **REQ-S3-03:** Upon receipt of a PFE module-discovered event, WorkHub shall automatically create a configuration task with the following fields:
  - `pfe_ref_type`: `module`
  - `pfe_ref_id`: module bus address (e.g., `0x0042`)
  - Task type: module configuration
  - Source module: PFE

#### 2.3.3 Worker Configuration Workflow Requirements

- **REQ-S3-04:** The worker shall receive an inbox notification for the newly created configuration task.
- **REQ-S3-05:** The task shall provide a guided step sequence for module configuration. The sequence for dimmer modules shall include:
  1. Open PFE (via deep link from task)
  2. Assign context to the new module
  3. Configure Common Mode Choke filter
  4. Configure RC low-pass filter matrix
  5. Test scene activation
  6. Verify configuration
- **REQ-S3-06:** WorkHub shall provide a direct deep-link from the task into the PFE configuration view for the specific module (`pfe_ref_id`), minimising navigation steps for the worker.

#### 2.3.4 Filter Matrix Configuration Requirements

- **REQ-S3-07:** The task completion record shall capture the filter parameters applied (Common Mode Choke settings, RC low-pass filter matrix values) as structured data, not free text.
- **REQ-S3-08:** PFE shall confirm successful configuration write to WorkHub via a configuration-confirmed event on the event bus before the task can be marked complete.

#### 2.3.5 Billing Add-on Requirements

- **REQ-S3-09:** Upon task completion, WorkHub shall emit a completion event to the billing subsystem with task type `module_configuration` and the module reference.
- **REQ-S3-10:** The billing subsystem shall create a billable add-on line on the relevant project invoice, referencing the module address and configuration task ID.

### 2.4 Avatar Role Change Request → Verification Task

**Reference Site:** Hotel Mitte — event week, Body Guard avatar

#### 2.4.1 Role Change Request Requirements

- **REQ-S4-01:** A client or authorised operator shall be able to submit a temporary role/access change request for a SCLAN avatar, specifying: avatar identifier, requested role (e.g., Body Guard), effective date range, and requester identity.
- **REQ-S4-02:** The role change request shall trigger PPT to create a verification task assigned to the responsible planner.
- **REQ-S4-03:** PPT shall emit a task-assignment event to WorkHub containing the verification task details and the role change request reference.

#### 2.4.2 Identity Verification Requirements

- **REQ-S4-04:** The planner assigned to the verification task shall be required to upload identity verification materials (badge photo and/or ID card scan) directly within WorkHub.
- **REQ-S4-05:** WorkHub shall enforce that at least one identity photo is uploaded before the verification task can be submitted as complete.
- **REQ-S4-06:** Uploaded identity materials shall be stored securely and linked to the task record and the audit log entry for this verification event.

#### 2.4.3 Approval and SCLAN Avatar Update Requirements

- **REQ-S4-07:** Upon task approval (planner submits completion with uploaded identity materials), WorkHub shall emit an avatar-role-approved event on the event bus.
- **REQ-S4-08:** The SCLAN avatar management subsystem shall receive the avatar-role-approved event and update the avatar's role and access permissions for the specified date range.
- **REQ-S4-09:** WorkHub shall record the verification outcome with: planner signature, uploaded identity photo references, approval timestamp, and new role assignment details.

#### 2.4.4 Audit Trail Requirements

- **REQ-S4-10:** All steps of the avatar role change process — request, task assignment, identity upload, approval, and role update — shall be written to the shared audit log with actor, timestamp, and module origin.
- **REQ-S4-11:** The audit trail for avatar role changes shall be immutable and retrievable by compliance officers without requiring WorkHub task access.

### 2.5 Energy Quota Anomaly → Investigation → Deep Sleep Firmware Fix

**Reference Site:** Logistics Hub Nord — irrigation segment

#### 2.5.1 Anomaly Detection and Alert Requirements

- **REQ-S5-01:** M-02 (Energy Intelligence) shall continuously monitor energy quota consumption per segment and emit an anomaly-detected event when consumption deviates beyond the configured threshold.
- **REQ-S5-02:** The anomaly-detected event shall include: segment identifier, anomaly type, deviation magnitude, timestamp, and current quota baseline.
- **REQ-S5-03:** PC-13 shall receive the M-02 anomaly-detected event and raise a PC-13 alert, then create a WorkHub investigation task referencing both the M-02 anomaly and the PC-13 alert.

#### 2.5.2 Investigation Task Requirements

- **REQ-S5-04:** The investigation task created by PC-13 shall have task type `investigation` and shall carry both the M-02 anomaly reference and the PC-13 alert reference in its metadata.
- **REQ-S5-05:** WorkHub shall notify the assigned worker and provide access to bus topology data, segment wiring diagrams, and firmware version information directly from the task context.

#### 2.5.3 Field Investigation Requirements

- **REQ-S5-06:** The worker shall be able to log investigation steps within the task, including: bus topology checks performed, cable tests executed, and firmware version readings.
- **REQ-S5-07:** WorkHub shall support structured diagnosis submission, capturing: root cause category, affected component, firmware version (found and required), and recommended fix action.

#### 2.5.4 Completion and Firmware Fix Task Creation Requirements

- **REQ-S5-08:** Upon investigation task completion, if the submitted diagnosis identifies a firmware issue, WorkHub shall automatically create a follow-on firmware update task with:
  - `pfe_ref_type`: `firmware`
  - Root cause reference linked to the investigation task
  - Target node and firmware version to be applied
- **REQ-S5-09:** The firmware update task shall be assigned according to the same worker or escalated per configured routing rules.

#### 2.5.5 Post-Fix Quota Re-baselining Requirements

- **REQ-S5-10:** Upon completion of the firmware update task, WorkHub shall emit a fix-complete event to M-02, referencing the original anomaly ID and the affected segment.
- **REQ-S5-11:** M-02 shall recalculate the energy quota baseline for the affected segment after receiving the fix-complete event, using consumption data from after the fix timestamp.
- **REQ-S5-12:** M-02 shall emit a baseline-updated event, and the new baseline shall be written to the audit log with the investigation task ID as reference.

#### 2.5.6 Full Audit Chain Requirements

- **REQ-S5-13:** The complete event chain — anomaly detection → PC-13 alert → investigation task → diagnosis → firmware fix task → firmware update → quota re-baseline — shall be traceable in the audit log as a linked chain using a shared anomaly correlation ID.

## 3. Cross-Module Event Requirements

### 3.1 Event Bus Requirements

- **REQ-EVT-01:** The event bus shall support both WebSocket (real-time push) and async queue (reliable delivery) transport modes. WorkHub task creation events shall use async queue to guarantee delivery.
- **REQ-EVT-02:** All events published on the bus shall include a standard envelope: `event_id`, `event_type`, `source_module`, `target_module` (or `broadcast`), `correlation_id`, `timestamp`, and `payload`.
- **REQ-EVT-03:** Events that trigger WorkHub task creation shall be idempotent: duplicate events carrying the same `correlation_id` shall not result in duplicate task creation.
- **REQ-EVT-04:** The event bus shall guarantee at-least-once delivery. WorkHub shall implement idempotency checks on all inbound task-creation events.

### 3.2 WorkHub Task Reference Fields

- **REQ-EVT-05:** Every WorkHub task created by an external module shall carry the following reference fields:
  - `source_module`: identifier of the originating module (e.g., `PC-13`, `PFE`, `M-02`, `PPT`)
  - `pfe_ref_type`: type of the originating entity (e.g., `fault`, `module`, `firmware`, `project`)
  - `pfe_ref_id`: unique identifier of the originating entity within the source module

- **REQ-EVT-06:** WorkHub shall expose a query API allowing external modules to retrieve task status by `pfe_ref_id` and `source_module`, enabling upstream modules to poll or verify task progress.

### 3.3 Completion Event Requirements

- **REQ-EVT-07:** All WorkHub task completion events shall include: `task_id`, `pfe_ref_type`, `pfe_ref_id`, `source_module`, `completion_timestamp`, `worker_id`, `labour_hours`, `materials` (list), `diagnosis` (if applicable), and `signature_reference`.
- **REQ-EVT-08:** Billing-relevant completion events shall be routed to the billing subsystem queue. Non-billing tasks (e.g., verification only) shall still emit completion events but shall be flagged `billable: false`.

### 3.4 Error and Retry Requirements

- **REQ-EVT-09:** If WorkHub fails to create a task from an inbound event within 60 seconds, the event bus shall retry delivery up to 3 times with exponential back-off before routing to a dead-letter queue.
- **REQ-EVT-10:** Operations staff shall be alerted when events enter the dead-letter queue. WorkHub shall provide a UI for manual task creation from dead-lettered events.

## 4. Definition of Done Requirements

### 4.1 Dual-Confirmation Model

- **REQ-DOD-01:** The WorkHub Definition of Done shall require dual-confirmation for all billable tasks: (1) worker submission of completion record, and (2) customer acknowledgement or signature.
- **REQ-DOD-02:** Neither confirmation alone shall be sufficient to mark a task as `done` and trigger downstream billing or module events. The task shall remain in `pending_confirmation` state until both are received.
- **REQ-DOD-03:** For commissioning tasks (Scenario 2), customer confirmation shall be provided via an eIDAS-compliant digital signature captured within WorkHub.
- **REQ-DOD-04:** For fault resolution tasks (Scenario 1), customer confirmation may be provided via a simplified sign-off (e.g., on-site digital signature or remote approval link), as configured per contract.

### 4.2 Non-Billable Task Completion

- **REQ-DOD-05:** Verification tasks (e.g., avatar role change, Scenario 4) shall not require customer dual-confirmation. Planner submission with uploaded evidence shall constitute completion.
- **REQ-DOD-06:** Investigation tasks (Scenario 5) shall be completed by worker submission alone; however, the follow-on firmware fix task shall require dual-confirmation if it generates a billable record.

### 4.3 Completion Record Contents

- **REQ-DOD-07:** Every task completion record shall include as a minimum: worker ID, completion timestamp, step-by-step work log, materials used (with quantities), labour hours (from timer), and any attachments (photos, identity documents, measurement data).
- **REQ-DOD-08:** Completion records shall be immutable once the dual-confirmation is finalised. Amendments shall require a new task or a documented amendment record linked to the original.

## 5. Audit and Traceability Requirements

### 5.1 Shared Audit Log

- **REQ-AUD-01:** All modules (WorkHub, PFE, PC-13, M-02, PPT, billing) shall write to a shared, append-only audit log.
- **REQ-AUD-02:** Each audit log entry shall contain: `log_id`, `timestamp`, `actor` (user or system), `source_module`, `event_type`, `entity_type`, `entity_id`, `correlation_id`, and a human-readable `description`.
- **REQ-AUD-03:** The audit log shall be queryable by `correlation_id` to reconstruct the full event chain for any scenario (fault, commissioning, anomaly investigation, etc.).

### 5.2 Traceability Requirements

- **REQ-AUD-04:** Every invoice line generated by the billing subsystem shall be traceable via `task_id` and `pfe_ref_id` back to the originating WorkHub task and further back to the originating module event.
- **REQ-AUD-05:** Every avatar role change shall be traceable from the original role change request through the verification task, identity upload, approval event, and SCLAN role update, all under a single correlation ID.
- **REQ-AUD-06:** Every firmware fix shall be traceable from the M-02 anomaly event through PC-13 alert, WorkHub investigation task, diagnosis, firmware update task, and M-02 re-baselining event.

### 5.3 Retention and Access Requirements

- **REQ-AUD-07:** Audit log entries shall be retained for a minimum of 7 years to comply with financial and operational record-keeping requirements.
- **REQ-AUD-08:** Read access to the audit log shall be role-gated. Compliance officers and system administrators shall have full read access. Workers shall have read access to entries related to their own tasks only.
- **REQ-AUD-09:** The audit log shall not be modifiable by any module or user after the entry is written. Corrections shall be recorded as new entries referencing the original entry ID.

## Appendix A: Reference Field Definitions

| Field | Description | Example Values |
|-------|-------------|---------------|
| `pfe_ref_type` | Category of the originating entity in the source module | `fault`, `module`, `firmware`, `project` |
| `pfe_ref_id` | Unique identifier of the originating entity | `fault_9f3a`, `0x0042`, `firmware_v2.3.1` |
| `source_module` | Identifier of the module that created the task | `PC-13`, `PFE`, `M-02`, `PPT` |
| `correlation_id` | Shared ID linking all events in a single incident or project chain | UUID generated at first event in chain |
| `task_type` | Classification of the WorkHub task | `fault_resolution`, `commissioning`, `module_configuration`, `verification`, `investigation`, `firmware_update` |

## Appendix B: Task State Transitions

```
[Created] → [Assigned] → [In Progress] → [Worker Submitted]
                                                  ↓
                                    [Pending Customer Confirmation]
                                                  ↓
                                    [Done] → [Billing Event Emitted]
                                                  ↓
                                    [Downstream Module Event Emitted]
```

For non-billable verification tasks:

```
[Created] → [Assigned] → [In Progress] → [Planner Submitted] → [Done]
                                                                   ↓
                                                  [Upstream Role/Status Update Emitted]
```
