WorkHub — Developer Integration Guide

Complete specification for integrating SCLAN M-08 WorkHub into the [mn]medianet SaaS platform. Covers API design, database schema, real-time sync, translation engine, legal compliance endpoints, and frontend migration from the prototype.

Module SCLAN M-08 Platform [mn]medianet SaaS Version 1.0-rc1 Status PRE-RELEASE Classification Confidential — NDA 5.0
API version v1 Prototype WorkHub_Application.html Help doc WorkHub_Help.html Last updated May 2026

Overview

WorkHub is the field work management module of SCLAN 5.0. The current deliverable is a self-contained HTML prototype (WorkHub_Application.html) that implements the complete frontend in vanilla JS. This document specifies how to extract that prototype into a production SaaS application backed by the existing [mn]medianet infrastructure.

The prototype contains: all UI components, a complete in-memory data model, the translation engine (calling Anthropic API directly from the browser), AI text correction, timer logic, print/PDF generation, a test avatar with 35 browser tests, and tooltip/help system. All of these work today. The integration task is to replace the in-memory data with persistent API calls, add authentication, and wire real-time sync.

⚠ Scope boundary

This document covers WorkHub (M-08) only. It does not cover the broader SCLAN M-02 Energy Intelligence, PC-13 Quota Anomaly Detection, or PFE integration — those are covered in their own modules. WorkHub reads task and project data only; it does not write to Domain Node configuration.

Key architectural decisions

  • Translation proxy — the Anthropic API key must never be exposed in the browser. The frontend calls /api/v1/translate and /api/v1/correct which proxy to Anthropic server-side. The translation cache in Redis is shared across all users — if user A translates "Zone B installieren" to Polish, user B gets it from cache instantly.
  • Timer is local-first — timer state lives in the browser. When the worker taps Stop, the completed entry is written to the API. If the network is down, entries queue locally (IndexedDB) and sync on reconnect. This prevents data loss on poor site connectivity.
  • Signatures and photos — stored as binary blobs in S3/R2. The API returns signed URLs. The completion record stores the URL, not the base64. The frontend currently stores base64 — this must be migrated.
  • WebSocket for real-time — planner assigns a task → worker's today list updates live. Worker completes task → manager kanban updates live. Use a single /ws/workhub?token=JWT connection per session.

API design principles

Base URL

https://api.sclan.io/v1/workhub

Conventions

  • All timestamps in ISO 8601 UTC: 2026-05-24T14:30:00.000Z
  • All monetary values in cents (integer) to avoid floating-point issues: unitPriceCents: 2490
  • Pagination via cursor: ?cursor=<id>&limit=50
  • Language passed as header: Accept-Language: de
  • Content language stored on record, not inferred
  • Soft deletes — records are never hard-deleted (legal retention)
  • All writes return the updated resource
  • Errors follow RFC 7807 Problem Details

PDF generation

Server-side PDF generation is preferred over browser window.print() for production. Use Puppeteer or WeasyPrint. The existing print HTML templates in the prototype can be used as the rendering source — serve them at a private route, render headless, return binary PDF. This gives consistent output across all devices and allows PDF to be attached to the customer email copy.

Authentication

JWT token structure

WorkHub uses the existing SCLAN SaaS JWT. Add a workhub claim to the payload:

{
  "sub": "user_01J...",
  "installationId": "inst_abc123",
  "workhub": {
    "role": "worker",          // worker | planner | manager | client | finance
    "workerId": "TK",         // links to workers table
    "permissions": ["tasks:read", "tasks:complete", "time:write"]
  },
  "iat": 1748000000,
  "exp": 1748086400
}

Role-based access

All API routes check the workhub.role claim. The middleware rejects requests where the role does not have the required permission. See the Permission Matrix section for the full breakdown.

🔑 Critical — never expose API keys

The Anthropic API key must live server-side only. The prototype calls the Anthropic API directly from the browser — this is acceptable for prototype development but must be changed before production. The /translate and /correct endpoints act as a proxy that adds the API key server-side and applies rate limiting and caching.

Translation push

When a translation completes server-side, push translation.ready to all connected clients who have requested the same text in the same language. This allows the translation cache to be shared across sessions — user A's translation immediately updates user B's screen without a new API call.

⚠ Completion is nearly immutable

Once done and a completion record exists with a customer signature, reopening the task does not delete the completion record — it archives it. A new completion record is created on the next completion. This preserves the signed document for legal retention.

Translation engine

Architecture

The prototype calls Anthropic directly from the browser with the API key in the request. This must become a server-side proxy for production.

// Frontend calls
async function translateText(text, targetLang) {
  const key = hashStr(text) + '::' + targetLang;
  if (TRANS_CACHE[key]) return TRANS_CACHE[key];  // local session cache

  const res = await fetch('/api/v1/workhub/translate', {
    method: 'POST',
    headers: { 'Authorization': `Bearer ${jwt}` },
    body: JSON.stringify({ text, targetLang })
  });
  const { translated, cached } = await res.json();
  TRANS_CACHE[key] = translated;
  return translated;
}
// Server-side translate endpoint (Node.js / Express)
router.post('/translate', requireWorkhubAuth, async (req, res) => {
  const { text, targetLang } = req.body;

  // Check Redis first
  const cacheKey = `wh:trans:${hash(text)}:${targetLang}`;
  const cached = await redis.get(cacheKey);
  if (cached) return res.json({ translated: cached, cached: true });

  // Proxy to Anthropic
  const result = await anthropic.messages.create({
    model: 'claude-sonnet-4-20250514',
    max_tokens: 400,
    messages: [{ role: 'user', content: buildTranslatePrompt(text, targetLang) }]
  });
  const translated = result.content[0].text.trim();

  // Store in Redis with 30-day TTL
  await redis.setex(cacheKey, 2592000, translated);

  // Broadcast to other connected sessions (optional)
  await pubsub.publish('translation.ready', { hash: hash(text), targetLang, translated });

  res.json({ translated, cached: false });
});

Caching strategy

  • L1 — Browser session: JS object, lives for session duration. Fast, no network.
  • L2 — Redis: 30-day TTL. Shared across all users and sessions. Hash key = SHA-256 of source text truncated to 16 chars + :: + lang code.
  • L3 — PostgreSQL (optional): Long-term persistent cache for high-frequency translations (task titles that appear 1000x per day). Populated from Redis on first hit above threshold.

Rate limiting

Apply per-installation rate limiting to the /translate and /correct endpoints. Suggested limits: 200 translation calls/min per installation, 50 correction calls/min. Cache hits do not count toward limits.

Timekeeping

Local-first timer

The timer runs entirely in the browser. No server call is made while the timer is running. Only on Stop does the frontend POST to /time-entries. This means:

  • Timer works with no network connection
  • If the browser crashes, the entry may be lost — mitigate with localStorage heartbeat (see Offline section)
  • Start time is trusted from the client — the server validates that started_at < ended_at and ended_at <= now() + 60s

Timer heartbeat (crash recovery)

// Write to localStorage every 30s while timer is running
setInterval(() => {
  if (TIMER.taskId && TIMER.startTime) {
    localStorage.setItem('wh_timer', JSON.stringify({
      taskId: TIMER.taskId,
      startTime: TIMER.startTime.toISOString(),
      elapsedSec: getTimerElapsed(TIMER.taskId)
    }));
  }
}, 30000);

// On app load, check for interrupted session
const saved = localStorage.getItem('wh_timer');
if (saved) {
  const t = JSON.parse(saved);
  showRecoveryDialog(t); // ask: "Continue timer for Task X or discard?"
}

Legal retention

Time entries must be retained for 2 years (§ 16 ArbZG). Implement this as a database-level constraint: no DELETE on time_entries is allowed — only soft archive via archived_at. The API endpoint DELETE /time-entries/:id should return 405 Method Not Allowed with a message referencing the retention law.

Signatures & identity

Upload flow

Request presigned URL

Frontend calls POST /files/upload-url with {type: 'signature', contentType: 'image/png', taskId}. Server returns {uploadUrl, key, expiresAt}.

Upload directly to S3

Frontend PUTs the PNG blob to the presigned URL. No server involvement — the upload goes directly to S3/R2.

Confirm upload

Frontend calls POST /files/confirm with {key, taskId, fileType: 'signature'}. Server verifies the object exists in S3, stores the URL in completion_records.signature_url, returns permanent URL.

Reference in completion

The completion record stores the S3 key (not base64). All subsequent reads use GET /files/:key which returns a short-lived signed read URL (15-min TTL).

Paper signature fallback

When a customer refuses to sign on screen, the worker prints the consent form (see GET /print/consent/:taskId), the customer signs with a pen, and the worker photographs the signed document. This photo is uploaded to S3 under the paper-signatures/ prefix and stored as paper_signature_url in the completion record.

The paper signature photo has the same legal weight as the digital signature for the purposes of service delivery confirmation under eIDAS Art. 3(10) — it is a reproduction of a handwritten signature with a documented chain of custody (worker photographed it, timestamped, reference number on the printed form).

POST/files/upload-urlUse type: 'paper-signature' to get a presigned URL for the paper form photo.

Immutability

Signatures are immutable once uploaded. The S3 bucket should have Object Lock enabled for signature and identity-photo prefixes. This prevents accidental or malicious deletion and supports the legal retention requirements under eIDAS.

Data protection

Signature images and identity photos contain personal biometric data (GDPR Art. 9 special category for biometric data used to uniquely identify a natural person). Mitigations:

  • Store under a separate S3 prefix with restricted IAM policy
  • Access only via short-lived signed URLs — never direct public URLs
  • Log all access in audit_log
  • Deletion path: on GDPR erasure request, replace with a tombstone file and update signature_url to null after retention period expires

// Background job — runs every 5 minutes
async function sendPendingEmailCopies() {
  const pending = await db.query(`
    SELECT cr.*, t.title, t.project_id, p.name AS project_name,
           p.customer_id, c.name AS customer_name
    FROM completion_records cr
    JOIN tasks t ON t.id = cr.task_id
    JOIN projects p ON p.id = t.project_id
    JOIN customers c ON c.id = p.customer_id
    WHERE cr.copy_email IS NOT NULL
      AND cr.copy_sent_at IS NULL
    LIMIT 50
  `);

  for (const record of pending.rows) {
    const pdfUrl = await generateCompletionPDF(record);
    await email.send({
      to: record.copy_email,
      subject: `Work order completion — ${record.title}`,
      template: 'completion-copy',
      data: { record, pdfUrl }
    });
    await db.query(
      'UPDATE completion_records SET copy_sent_at = NOW() WHERE id = $1',
      [record.id]
    );
  }
}

Installation scoping

Every WorkHub record belongs to an installation. This is enforced at the database level via installation_id foreign keys and at the API level via JWT claim. No cross-installation data access is possible.

PFE integration

PFE (SCLAN Programming and Field Environment) is the live editor and viewer for SCLAN installations. It is not a data store — it reads and edits the state of hardware modules (Domain Nodes, SCLAN devices) directly over the bus, and surfaces SaaS module state for human inspection. WorkHub does not go through PFE — it communicates with modules directly via API and webhooks. PFE is a parallel tool that humans use alongside WorkHub.

🎛 What PFE actually is

PFE is a live editor and viewer — not a backbone, not a data store. When a technician opens PFE for an installation, they see the live state of every Domain Node, every module, every segment, every avatar — read directly from the hardware over the bus. When they edit a scene, that change is written directly to the module's own SME (State Machine Engine) stored in the module's firmware. PFE is the tool through which this editing happens. The module owns its state — PFE is just the interface.

WorkHub tasks that reference PFE objects (e.g. pfe_ref_type: 'fault') are triggering WorkHub to call the relevant module's API directly — the PFE reference is a semantic label identifying which hardware/software module object the task relates to.

PFE Live Monitor — worker presence

The PFE Live Monitor view shows the real-time state of a SCLAN installation — bus speeds, energy readings, active avatars, fault states. When WorkHub timer events are pushed to PFE, the Live Monitor adds a worker presence layer:

  • When a worker starts a timer → their name and task appear on the relevant segment/node in the Live Monitor
  • While timer is running → a live elapsed time counter shows next to their name
  • When timer stops → presence indicator clears
  • Multiple workers on same installation → all shown simultaneously

This allows the manager or planner watching PFE Live Monitor to see exactly which technician is working on which part of the bus, in real time, without switching to WorkHub.

Commissioning workflow — end-to-end

The most important PFE–WorkHub interaction is the commissioning workflow. When a new SCLAN installation is being set up, PFE maintains a commissioning state machine. WorkHub tasks map directly to commissioning steps:

PFE creates commissioning project

Planner opens PFE for new installation. Creates commissioning project with standard steps: cable survey, Domain Node mounting, bus termination, PnP discovery, context assignment, scene programming, energy quota setup, client walkthrough, sign-off.

PFE pushes commissioning tasks to WorkHub

Each commissioning step becomes a WorkHub task via pfe.commissioning.step_ready webhook. Tasks appear in the planner's WorkHub with pfe_ref_type: 'commissioning_step'. Planner assigns to field technicians.

Technician works on site

Worker sees task in WorkHub Today list. Starts timer. Completes physical work. Fills in completion note (AI-corrected). Logs materials (cable lengths, hardware serial numbers). Takes photos.

Task completion advances PFE step

Worker submits completion. WorkHub calls POST /pfe/commissioning/:stepId/complete with the completion note and worker ID. PFE advances its commissioning state machine. The next step becomes available.

Materials update PFE inventory

Any hardware materials logged (Domain Nodes, cables, modules) are pushed to POST /pfe/inventory/:installationId. PFE now knows exactly what hardware is installed where, with the installation date from the WorkHub time entry.

Client sign-off in WorkHub closes PFE commissioning

When the final commissioning task (client walkthrough + sign-off) is completed in WorkHub with a customer signature, WorkHub calls POST /pfe/commissioning/:id/close with the signature reference. PFE marks the installation as commissioned. The completion certificate becomes the handover document.

WorkHub task creation from PFE — implementation

// PFE webhook handler in WorkHub backend
router.post('/webhooks/pfe', verifyPfeSignature, async (req, res) => {
  const { event, installationId, data } = req.body;

  switch (event) {

    case 'pfe.module.discovered': {
      const settings = await getInstallationSettings(installationId);
      if (!settings.autoCreateTasksOnPnP) break;
      await createTask({
        installationId,
        title: `Configure ${data.moduleType} module ${data.moduleId} on segment ${data.segmentId}`,
        description: `Module discovered via PnP on Node ${data.nodeId}. Assign contexts, configure filter matrix, verify in PFE scene editor. Firmware: ${data.firmwareVersion}.`,
        priority: 'medium',
        pfe_ref_type: 'module',
        pfe_ref_id: data.moduleId,
        pfe_installation_id: installationId,
        pfe_completion_action: {
          action: 'mark_module_configured',
          moduleId: data.moduleId,
          nodeId: data.nodeId
        }
      });
      break;
    }

    case 'pfe.fault.detected': {
      // Always create — safety critical
      await createTask({
        installationId,
        title: `Fault: ${data.faultType} on ${data.segmentName} (Node ${data.nodeId})`,
        description: buildFaultDescription(data),
        priority: 'high',
        pfe_ref_type: 'fault',
        pfe_ref_id: data.faultId,
        pfe_installation_id: installationId,
        pfe_completion_action: {
          action: 'resolve_fault',
          faultId: data.faultId,
          nodeId: data.nodeId,
          segmentId: data.segmentId
        }
      });
      // Also push to worker inbox immediately
      await notifyAssignedWorker(installationId, 'Urgent fault alert');
      break;
    }

    case 'pfe.node.offline': {
      await createTask({
        installationId,
        title: `Domain Node ${data.nodeId} offline — investigate`,
        priority: 'high',
        pfe_ref_type: 'node',
        pfe_ref_id: data.nodeId,
        pfe_installation_id: installationId
      });
      break;
    }
  }
  res.sendStatus(200);
});

Security — PFE bridge

  • All PFE webhook calls are signed with HMAC-SHA256 using a shared secret per installation. Verify the X-PFE-Signature header before processing.
  • All WorkHub → PFE API calls use a service account JWT scoped to the installation, not user JWTs.
  • PFE bridge calls are rate-limited separately from user API calls. Default: 1000 events/hour per installation.
  • PFE bridge is disabled if the installation has no active WorkHub subscription — PFE events are queued for 24h then dropped.

For the initial WorkHub production release, implement PFE integration in this order:

  1. Read installation + node/segment names — populates task descriptions with real location context
  2. Fault webhook → auto task creation — highest operational value, safety-critical
  3. Timer → worker presence in Live Monitor — real-time visibility for managers
  4. Commissioning step sync — needed for new installations
  5. Materials → inventory — hardware tracking
  6. Field notes → installation docs — documentation quality

PFE as platform spine — WorkHub in context

WorkHub is not a standalone work management tool. It is the field execution layer of the SCLAN SaaS platform — one of several modules that each own their own data and communicate directly with each other. PFE is not the connective tissue between them — it is a separate tool that humans use to view and edit module state. The modules interoperate directly.

🧬 Corrected architectural principle

Each module owns its own truth. PFE is the live editor and viewer — not a data store.

PFE is a tool — a unified interface through which a technician or planner can view and edit the state of any SCLAN hardware or software module. It does not store that state. The truth lives in the modules themselves:

  • Domain Nodes own their SME (State Machine Engine), BOPT results, ML fault counters, energy measurements — stored in their own firmware flash. PFE reads and edits these live over the bus.
  • Each SCLAN hardware module owns its own filter matrix, context assignments, bus parameters — stored locally on the device. PFE surfaces them for editing.
  • Each SaaS module (WorkHub, M-02, PC-13, Billing, PPT) owns its own database. PFE does not mediate between them — they communicate directly with each other via API and webhooks.

Removing PFE does not affect any module's data. The Domain Nodes keep running. WorkHub keeps recording time. PC-13 keeps detecting anomalies. PFE is a lens — not the backbone.

PPT → WorkHub → PFE: the full loop

Planner creates sprint in PPT

Selects tasks from backlog (generated by PFE commissioning steps + PC-13 fault tasks + manual). Assigns story points, sets dependencies, computes critical path. Sprint capacity checked against WorkHub worker availability (reads GET /workhub/workers/:id/capacity).

PPT pushes tasks to WorkHub with sprint metadata

Each task in the sprint appears in the assigned worker's WorkHub today list on the sprint start date. Task carries: sprint_id, story_points, dependencies, milestone links. Worker sees none of the planning metadata — just the task title, description, estimate, and priority.

Worker executes in WorkHub

Timer, completion note, materials, signature — all the standard WorkHub flow. WorkHub pushes completion event to PPT via WebSocket (task.completed). PPT updates burndown chart in real time. If task is on critical path, PPT recalculates float for remaining tasks.

WorkHub completion triggers PFE validation

If the task has a pfe_completion_action, PFE is updated: commissioning step advanced, fault closed, module marked configured. PFE state is the ground truth — PPT marks the task truly done only after PFE confirms the step.

PPT sprint review: PFE as acceptance criterion

At sprint review, PPT shows two things: WorkHub says task is done (completion note + signature), AND PFE confirms the physical reality changed (commissioning step advanced, bus verified, module active). A task cannot be "Done" in the Scrum sense until both layers agree.

Billing M-09 closes the loop

Sprint completion triggers M-09 to assemble the sprint invoice: all completed tasks' labour and materials, grouped by project. Milestone completions can trigger contract payment stages automatically.

PFE (PFE is a live editor/viewer — technicians use it to inspect and edit module state directly. It does not mediate data between modules. Modules talk to each other via direct API/webhooks.)
📐 PPT implementation note

PPT does not yet exist as a built module. The WorkHub data model is designed to accommodate it from day one — the sprint_id, story_points, depends_on, and milestone_id fields are defined in the schema now, even though PPT has not written them yet. When PPT is built, it writes into an existing schema. WorkHub workers never see these fields — they are planning-layer metadata only.
